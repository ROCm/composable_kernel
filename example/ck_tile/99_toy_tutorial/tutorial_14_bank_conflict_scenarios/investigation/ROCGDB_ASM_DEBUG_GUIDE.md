# Debugging Assembly (.s) Files with rocgdb

## The Problem

When you run `rocgdb` and use `disassemble`, it shows optimized runtime code that doesn't match the `.s` file generated by the compiler. The `.s` file is the **ground truth** showing actual GPU instructions (like `ds_read_b16`), but rocgdb doesn't automatically show it.

## Solution: Debug the .s File Directly

### Step 1: Compile with Debug Info and Keep Assembly

```bash
cd /data0/aghamari/composable_kernel/build

# Compile with -g (debug symbols) and -save-temps (keep .s file)
hipcc --offload-arch=gfx942 -g -save-temps=obj \
    ../example/ck_tile/99_toy_tutorial/tutorial_14_bank_conflict_scenarios/08_force_lds_reads.cpp \
    -I../include -I../library/include -I../example/ck_tile \
    -std=c++20 -o tutorial_08_debug
```

This generates:
- `tutorial_08_debug` - executable with debug symbols
- `08_force_lds_reads-hip-amdgcn-amd-amdhsa-gfx942.s` - GPU assembly file

### Step 2: Find Key Assembly Labels/Lines

Look at the .s file to find where to set breakpoints:

```bash
cat 08_force_lds_reads-hip-amdgcn-amd-amdhsa-gfx942.s
```

Key locations:
- Line 8: `_Z22force_lds_reads_kernelPDF16_:` - Kernel entry
- Line 17: `ds_write_b16 v1, v2` - LDS write instruction
- Line 21: `s_barrier` - Barrier/sync point
- Line 29: `ds_read_u16 v0, v0` - LDS read instruction

### Step 3: Start rocgdb and Set Breakpoints

```bash
rocgdb ./tutorial_08_debug
```

Inside rocgdb:

```gdb
# Set breakpoint at kernel function (by mangled name from .s file)
(gdb) break _Z22force_lds_reads_kernelPDF16_
Breakpoint 1 at ...

# Run the program
(gdb) run

# Program will hit breakpoint when kernel launches
# rocgdb will show: Thread X hit Breakpoint 1, with lanes [0-63]

# Now you're in the GPU kernel!
```

### Step 4: Navigate to Specific Instructions

#### Method A: Step Through Instructions

```gdb
# Step one GPU instruction at a time
(gdb) stepi

# Repeat stepi until you reach the ds_write or ds_read
(gdb) stepi
(gdb) stepi
...

# Check where you are
(gdb) x/i $pc
# Shows current instruction
```

#### Method B: Set Breakpoint at Specific Instruction Address

First, disassemble to see addresses:

```gdb
(gdb) disassemble _Z22force_lds_reads_kernelPDF16_
# This shows addresses like:
#   0x... <+0>:  v_cmp_gt_u32_e32 vcc, 64, v0
#   0x... <+4>:  v_lshlrev_b32_e32 v1, 1, v0
#   ...
#   0x... <+X>:  ds_write_b16 v1, v2    <-- Find this one
```

Count instructions to estimate offset, then:

```gdb
# If ds_write is at offset +28 (for example)
(gdb) break *_Z22force_lds_reads_kernelPDF16_+28

# Or use absolute address if you found it
(gdb) break *0x<address>
```

#### Method C: Use Assembly Label Breakpoints (if available)

Some assembly has labels like `.LBB0_2`:

```gdb
# Set breakpoint at label
(gdb) break .LBB0_2
```

### Step 5: Inspect GPU State at LDS Instructions

Once you're at a `ds_write_b16` or `ds_read_u16` instruction:

#### Check Current Instruction

```gdb
(gdb) x/i $pc
# Shows: ds_write_b16 v1, v2
```

#### View Vector Registers (VGPRs)

```gdb
# Show all VGPRs
(gdb) info registers

# Show specific VGPR
(gdb) info registers v0
(gdb) info registers v1
(gdb) info registers v2

# For ds_write_b16 v1, v2:
#   v1 = LDS address (offset in bytes)
#   v2 = Value to write
```

#### View LDS Memory

```gdb
# View LDS memory as 16-bit values (FP16)
(gdb) x/64hh <lds_base_address>

# If you have the __shared__ variable name:
(gdb) x/64hh &lds_memory
```

#### Switch Between GPU Lanes

```gdb
# List all active GPU threads/lanes
(gdb) info threads

# Output shows lanes like:
#   Thread 7 (AMDGPU Lane 1:2:1:1/0) - lane 0
#   Thread 8 (AMDGPU Lane 1:2:1:1/1) - lane 1
#   ...

# Switch to different lane
(gdb) thread 8
# Now you see registers for lane 1

# Check what this lane is doing
(gdb) info registers v0 v1 v2
```

### Step 6: Step Over ds_write and Verify LDS Contents

```gdb
# At ds_write_b16 instruction
(gdb) x/i $pc
0x...: ds_write_b16 v1, v2

# Check what will be written
(gdb) info registers v1  # Address
(gdb) info registers v2  # Value

# Execute the instruction
(gdb) stepi

# Wait for write to complete (ds operations are asynchronous)
# Step a few more times until s_waitcnt
(gdb) stepi
(gdb) stepi
# Keep going until you see s_waitcnt lgkmcnt(0)

# Now check LDS memory - should see the written value
(gdb) x/64hh &lds_memory
```

### Step 7: Debug Across All Lanes

To see what multiple lanes are doing:

```gdb
# Define a helper to print v1 for all lanes
(gdb) thread apply all info registers v1

# Or create a script to iterate through lanes
(gdb) set $i = 7
(gdb) while $i < 71
  thread $i
  printf "Lane %d v1 = ", $i-7
  info registers v1
  set $i = $i + 1
end
```

## Complete Example Session

```bash
# Build with debug
cd /data0/aghamari/composable_kernel/build
hipcc --offload-arch=gfx942 -g -save-temps=obj \
    ../example/ck_tile/99_toy_tutorial/tutorial_14_bank_conflict_scenarios/08_force_lds_reads.cpp \
    -I../include -I../library/include -I../example/ck_tile -std=c++20 -o tut08_dbg

# Check .s file for instruction locations
grep -n "ds_" 08_force_lds_reads-hip-amdgcn-amd-amdhsa-gfx942.s
# Output:
# 17:	ds_write_b16 v1, v2
# 29:	ds_read_u16 v0, v0

# Start debugger
rocgdb ./tut08_dbg
```

Inside rocgdb:

```gdb
# Break at kernel
(gdb) break _Z22force_lds_reads_kernelPDF16_
(gdb) run

# Hit breakpoint in GPU kernel
Thread 7 ... hit Breakpoint 1 ...

# Step to ds_write instruction (need to count stepi calls)
# Or estimate offset and break there
(gdb) disassemble
# Find ds_write address or offset

# Set breakpoint at ds_write (adjust offset based on disassemble output)
(gdb) break *_Z22force_lds_reads_kernelPDF16_+28
(gdb) continue

# Now at ds_write
(gdb) x/i $pc
# Shows: ds_write_b16 v1, v2

# Check registers for lane 0
(gdb) info registers v0 v1 v2
# v0 = thread ID
# v1 = LDS address (tid * 2, since FP16 = 2 bytes)
# v2 = FP16 value being written

# Switch to lane 5 to see what it's writing
(gdb) thread 12  # Assuming lane 5 is thread 12
(gdb) info registers v0 v1 v2

# Execute the write
(gdb) stepi

# Continue to barrier
(gdb) until *_Z22force_lds_reads_kernelPDF16_+XX  # Address of s_barrier

# After barrier, set breakpoint at ds_read
(gdb) break *_Z22force_lds_reads_kernelPDF16_+YY  # Address of ds_read_u16
(gdb) continue

# At ds_read
(gdb) x/i $pc
# Shows: ds_read_u16 v0, v0

# v0 contains read address = (tid+1)%64 * 2
(gdb) info registers v0

# Execute read
(gdb) stepi

# After s_waitcnt, v0 contains the read value
(gdb) stepi  # Step past ds_read
(gdb) stepi  # Step to s_waitcnt
(gdb) stepi  # Step past s_waitcnt

(gdb) info registers v0
# Now v0 has the FP16 value read from LDS
```

## Tips

### Finding Instruction Offsets

```gdb
# After breaking at kernel, count instructions
(gdb) disassemble _Z22force_lds_reads_kernelPDF16_
# Manually count to find ds_write/ds_read offset
```

### Watching LDS Bank Conflicts

At `ds_read` instruction, check addresses across lanes:

```gdb
# For each lane, record the LDS address in v0
(gdb) thread 7   # Lane 0
(gdb) print $v0
(gdb) thread 8   # Lane 1
(gdb) print $v0
# ...

# Calculate banks: (address / 4) % 32
# If multiple lanes access same bank = bank conflict
```

### Using .s File as Reference

Keep the .s file open in another window:

```bash
# In another terminal
cat -n 08_force_lds_reads-hip-amdgcn-amd-amdhsa-gfx942.s | less
```

Match rocgdb's instruction addresses to line numbers in .s file.

## Limitations

- rocgdb's `disassemble` output might not exactly match .s file (optimizations, reordering)
- Some instructions might be hard to find by offset
- LDS memory viewing might require knowing base address
- Thread/lane switching can be tedious for 64 lanes

## Advanced: Attach .s File as Source in rocgdb

You can tell rocgdb to use the .s file as source code!

### Method 1: Using directory command

```gdb
# Tell rocgdb where to find source files
(gdb) directory /data0/aghamari/composable_kernel/build

# Now when you break, rocgdb might show .s file lines
(gdb) break _Z22force_lds_reads_kernelPDF16_
(gdb) run

# Try to list source
(gdb) list
```

### Method 2: Using substitute-path

```gdb
# Map the source path
(gdb) set substitute-path /build-path/ /data0/aghamari/composable_kernel/build/

# Break and run
(gdb) break _Z22force_lds_reads_kernelPDF16_
(gdb) run
(gdb) list
```

### Method 3: Set breakpoint by .s file line number

If rocgdb knows about the .s file:

```gdb
# Break at line 17 (ds_write_b16) in the .s file
(gdb) break 08_force_lds_reads-hip-amdgcn-amd-amdhsa-gfx942.s:17

# Break at line 29 (ds_read_u16)
(gdb) break 08_force_lds_reads-hip-amdgcn-amd-amdhsa-gfx942.s:29

(gdb) run

# When hit, you can step through assembly source
(gdb) list
# Shows lines from .s file!

(gdb) next  # Go to next assembly line
(gdb) stepi # Step one instruction
```

### Method 4: Compile .s file directly with debug symbols

```bash
# Assemble the .s file with debug info
/opt/rocm/llvm/bin/clang -g -target amdgcn-amd-amdhsa -mcpu=gfx942 \
    -c 08_force_lds_reads-hip-amdgcn-amd-amdhsa-gfx942.s \
    -o gpu_kernel.o

# This embeds .s file path into debug info
# Then link it with your program
```

### Verify Source Path in Binary

```bash
# Check if debug info points to .s file
readelf --debug-dump=line ./tutorial_08_debug | grep "\.s"
```

## Alternative: Use the .s File Directly for Analysis

For detailed bank conflict analysis, you might prefer to:
1. Read the .s file to understand the access pattern
2. Manually calculate which lanes access which banks
3. Use rocgdb only to verify register values at key points

The .s file is the **source of truth** for GPU assembly!
